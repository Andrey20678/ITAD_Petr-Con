# Отчёт о качестве: Bike Sharing (`hour.csv`)

## 1. Контекст

Вопрос из [Project Brief](project_brief.md): в какие часы суток, дни недели и сезоны наблюдаются
наибольшие и наименьшие значения почасового спроса (`cnt`), и как в этих срезах различается
соотношение `casual` и `registered`.

- Гранулярность: одна строка `hour.csv` описывает один час работы системы проката Capital Bikeshare.
- Бизнес-ключ: `(dteday, hr)`. Отдельного идентификатора поездки в наборе нет - данные уже
  агрегированы до часа, поэтому уникальность проверяется по ключу, а `instant` считается
  техническим индексом и в правилах не используется.
- `day.csv` используется только как справочник для проверки согласованности дневных
  и почасовых сумм (уточняющий вопрос 2), сам в staging не записывается.

Входные файлы:

```text
s3://raw/bike_sharing/ingested_on=2026-11-02/hour.csv
s3://raw/bike_sharing/ingested_on=2026-11-02/day.csv
```

Логическая дата загрузки ingested_on - `2026-11-02`; аналитический период - весь снимок
2011-01-01…2012-12-31. raw в ходе работы не изменяется; day.csv только читается.

## 2. Профиль
Размер: 17 379 строк, 17 полей. По всем восьми выбранным для задачи полям пропусков нет:
Поле | Тип | Примеры | Пропуски / доля
-|-|-|-
dteday | DATE | 2011-01-01, 2011-01-02 | 0 / 0 %
hr | BIGINT | 0, 1 | 0 / 0 %
cnt | BIGINT | 1, 2 | 0 / 0 %
casual | BIGINT | 0, 1 | 0 / 0 %
registered | BIGINT | 0, 1 | 0 / 0 %
weathersit | BIGINT | 1, 2 | 0 / 0 %
season | BIGINT | 1, 2 | 0 / 0 %
weekday | BIGINT | 0, 1 | 0 / 0 %

Ключ и покрытие (способ подсчёта: GROUP BY dteday, hr HAVING count(*) > 1 для повторов;
count(*) − count(distinct *) для полных дублей):
Ключей с повторами | Избыточных строк | Полных дублей | Дней | Строк | Не хватает часов | min dteday | max dteday
-|-|-|-|-|-|-|-
0 | 0 | 0 | 731 | 17 379 | 165 | 2011-01-01 | 2012-12-31

Распределение по часу суток (фрагмент, 5 самых «нагруженных» и самый тихий час):
Час | Записей | Прокатов | Средний cnt
-|-|-|-
17 | 730 | 336 860 | 461,5
18 | 728 | 309 772 | 425,5
16 | 730 | 227 748 | 312,0
19 | 728 | 226 789 | 311,5
8 | 727 | 261 001 | 359,0
4 | 697 | 4 428 | 6,4

Значимые наблюдения:

1. Покрытие неполное. 731 день × 24 = 17 544 возможных слота против 17 379 фактических
строк: отсутствуют 165 часовых записей. Это ограничивает усреднения по часу (avg(cnt))
и сверку с day.csv: часть суточных итогов собирается из неполного набора часов.

2. Спрос сильно концентрирован по часам. Вечерний пик (17:00, 461,5 прокатов/час)
в ~72 раза больше ночного минимума (04:00, 6,4 прокатов/час). Это подтверждает
постановку основного вопроса Brief: часовой срез является ключевым, а сравнение
casual/registered имеет смысл именно в нём.

Нарушений не обнаружено, поэтому вместо примеров проблемных записей
здесь зафиксированы подтверждённые свойства: 0 пропусков, 0 повторов ключа,
0 отрицательных счётчиков, cnt = casual + registered во всех 17 379 строках.

## 3. Правила и результаты

Условия, проверяемые строки, критичность, действия и связь с задачей описаны
в разделе «Шаг 3» ноутбука рядом с конкретными
SQL-запросами. Пороги заданы переменными в ячейках. Действие quarantine применяется
к критическим нарушениям, flag оставляет запись в staging с явным признаком, report_only только отражает результат в сводке.

Правило | Проверено | Нарушений | Доля | Порог | Сравнение | Действие
-|-|-|-|-|-|-
hour_key_unique | 17 379 строк | 0 | 0 % | count ≤ 0 | Не превышен. | quarantine
required_fields_present | 17 379 строк | 0 | 0 % | count ≤ 0 | Не превышен. | quarantine
hr_in_range | 17 379 строк | 0 | 0 % | count ≤ 0 | Не превышен. | quarantine
weathersit_in_domain | 17 379 строк | 0 | 0 % | count ≤ 0 | Не превышен. | flag
cnt_equals_casual_plus_registered | 17 379 строк | 0 | 0 % | count ≤ 0 | Не превышен. | quarantine
non_negative_counts | 17 379 строк | 0 | 0 % | count ≤ 0 | Не превышен. | quarantine
hour_day_cnt_consistent | 731 день | 0 | 0 % | count ≤ 0 | Не превышен. | report_only

Решения по действиям:

* quarantine выбрано для hour_key_unique, required_fields_present, hr_in_range,
cnt_equals_casual_plus_registered, non_negative_counts, потому что любое нарушение
этих правил напрямую искажает основную метрику cnt и/или часовой срез - такие строки
нельзя безопасно использовать в анализе.

* flag для weathersit_in_domain выбран, потому что недопустимый код weathersit,
season или weekday не искажает сам cnt, а только ломает категориальный срез;
такие записи полезно сохранить, но пометить, чтобы аналитик мог исключить их по признаку.
В этом снимке нарушений нет, поэтому признак quality_weathersit_in_domain_violated
равен false во всех 17 379 строках.

* report_only для hour_day_cnt_consistent потому, что расхождение sum(hour.cnt) и
day.cnt - свойство снимка (в т.ч. следствие 165 недостающих часов), а не «плохая»
часовая запись; за него нельзя наказывать карантином.

Карантин пуст, поэтому записей с исключением и сохранением с флагом нет.

## 4. Подготовленные данные

Выходные пути в staging:
``` text
s3://staging/bike_sharing/source_ingested_on=2026-11-02/staging.parquet
s3://staging/bike_sharing/source_ingested_on=2026-11-02/quarantine.parquet
```

Фактические изменения схемы:

* Имена и типы исходных полей сохранены; единственное преобразование -
read_csv_auto уже приводит dteday к типу DATE (в CSV это текст YYYY-MM-DD).

* В staging.parquet добавлен признак quality_weathersit_in_domain_violated
(BOOLEAN): true - нарушение домена категорий weathersit/season/weekday,
false - нарушения нет. Смысл - не «исправление» значения, а флаг для последующей фильтрации.

* instant оставлен как исходное техническое поле; в анализе не используется.

* В quarantine.parquet дополнительно к исходным полям хранятся quality_rule_ids
(идентификаторы критических правил через ;, например hour_key_unique;hr_in_range;)
и quarantine_reason (читаемое объяснение). Так как карантин пуст, файл содержит
0 строк, но с корректной схемой (DESCRIBE saved_quarantine показывает все поля).

Техническое поле source_ingested_on DATE появляется при чтении из S3 как Hive-раздел,
добавляемый DuckDB из имени каталога; внутри самого Parquet-файла его нет. Это не
преобразование данных, а следствие структуры пути.

Баланс строк: 17 379 (raw) = 17 379 (staging) + 0 (карантин). Ни одна запись не удалена и не добавлена.

Проверки на прочитанном staging.parquet:

* нарушений критических правил (hour_key_unique, required_fields_present,
hr_in_range, cnt_equals_casual_plus_registered, non_negative_counts) - 0;

* значений quality_weathersit_in_domain_violated = true - 0;

* бизнес-агрегаций нет, поле instant сохранено «как есть», raw не изменялся.

## 5. Воспроизводимость и ограничения

Ноутбук notebooks/profile_quality.ipynb выполнен дважды
с перезапуском ядра Jupyter. Выполнялись все ячейки сверху вниз, входной путь, период, пороги и выходной префикс не менялись.

Результат (чтение через S3) | Первое выполнение | Повторное выполнение
-|-|-
Raw | 17 379 | 17 379
Staging | 17 379 | 17 379
Карантин | 0 | 0
Флаги weathersit_in_domain | 0 | 0
Критические нарушения в staging | 0 | 0

Ограничения дальнейшего анализа:
* Неполное покрытие часов (165 пропусков из 17 544). Средние по часу и сверка
с day.csv считаются на неполном наборе; для дневных итогов часть часов не учтена.
Прежде чем агрегировать по часу или дню, нужно определить политику обработки
пропущенных часов (например, «не восстанавливать, а фиксировать как ограничение»).

* Агрегированность данных. Набор описывает счётчики за час, а не отдельные поездки;
причинные выводы о поведении пользователей по этому набору невозможны. Погодные признаки
нормализованы, поэтому для интерпретации нужно умножать их на делители из Readme.txt.
